# Multi-Platform Local-First App: Architecture & Build Plan

**Agent Directive:** You are building a multi-platform (Web and Native Desktop) local-first application. The core business logic is written in Go, the UI is built with React, and the data layer uses a split-storage model (Filesystem + SQLite). You must strictly adhere to the architecture and constraints defined below.

## 1. Core Architecture & Constraints

* **Monorepo Strategy:** Single repository containing Go backend, WebAssembly bridges, and React frontend.
* **Web Target (Browser):** Compiled using **TinyGo** targeting `wasi` (WebAssembly Component Model), transpiled to an ES Module using `@bytecodealliance/jco`.
* *Constraint:* Do NOT use `GOOS=js GOARCH=wasm` or `syscall/js`. Do NOT use standard Go SQLite drivers here, as TinyGo does not support CGO.


* **Desktop Target:** Bundled using the **Wails v2** framework. Uses standard Go and a pure-Go SQLite driver (`modernc.org/sqlite`) to avoid CGO cross-compilation issues.
* **Split-Storage Data Model (Crucial):**
* **Source of Truth:** JSON files written to the filesystem.
* **Index:** SQLite is used purely to index metadata from these JSON files to avoid slow, full-directory scans.
* **Write Flow:** Create `.lock` file -> Write JSON -> Update SQLite Index -> Remove `.lock` -> Emit UI Event.
* **Recovery:** A `rebuild-index` command must exist to scan the JSON files and rebuild the SQLite index from scratch.


* **Filesystem & Database Routing:**
* **Desktop:** Go uses standard `os` package pointing to the native user data directory (e.g., `~/.config/myapp`), and standard `database/sql` for the native SQLite file.
* **Web:** Go uses standard `os` package. TinyGo translates these to WASI calls. The JS Web Worker must map the WASI root (`/`) to the browser's **OPFS** root using `@bytecodealliance/preview2-shim`. SQLite queries are executed by passing them through a WIT host capability to `@sqlite.org/sqlite-wasm` running in the JS worker.

## 3. Implementation Phases

### Phase 1: The Contract (`api/vfs.wit`)

Define the API Go exposes to React, and the capabilities Go imports from JavaScript. Run `wit-bindgen go` to generate bindings.

```wit
package localfirst:vfs;

interface sqlite-host {
    execute-query: func(sql: string, params: list<string>) -> string;
}

interface event-host {
    emit-event: func(topic: string, payload: string);
}

interface types {
    record command-result {
        success: bool,
        output: string,
        error-message: option<string>,
    }
}

world app {
    import sqlite-host;
    import event-host;
    use types.{command-result};
    export execute-cli: func(args: list<string>) -> command-result;
}

```

### Phase 2: Go Abstractions (`internal/`)

Implement the build-tag swapped interfaces for your dependencies:

1. **`vfs`:** Expose a `GetRoot()` function. Native returns OS config dir; WASM returns `/`.
2. **`db`:** Expose a `QueryExecutor` interface. Native uses `modernc.org/sqlite`; WASM calls the generated `sqlite_host.ExecuteQuery`.
3. **`events`:** Expose an `Emit` function. Native uses Wails `runtime.EventsEmit`; WASM calls `event_host.EmitEvent`.

### Phase 3: The Synchronization Engine (`internal/engine`)

Write the shared business logic. When executing a command like `create-record`, the engine MUST use standard Go `os` operations:

```go
root := vfs.GetRoot()
filePath := filepath.Join(root, "data", id+".json")

// 1. Write source of truth
os.WriteFile(filePath, jsonData, 0644)

// 2. Update SQLite index
db.Instance.ExecuteQuery("INSERT INTO index...", ...)

// 3. Emit reactivity event
events.Emit("data-changed", id)

```

### Phase 4: Web Worker & WASI OPFS Setup (`frontend/src/worker.ts`)

This is the most critical integration file. Use `comlink` to expose the worker to React.

1. **Request OPFS:** `const opfsRoot = await navigator.storage.getDirectory();`
2. **Mount WASI:** Use `setPreopens({ '/': opfsRoot })` from `@bytecodealliance/preview2-shim`. *This allows TinyGo's `os.WriteFile` to write directly to the browser filesystem.*
3. **Initialize SQLite:** Boot `@sqlite.org/sqlite-wasm` and configure it to use OPFS for its `.sqlite3` index file.
4. **Inject Capabilities:** When instantiating the JCO module, inject the `sqlite-host` and `event-host` functions.
5. **Route Events:** When WASM calls `event-host.emit-event`, route it to callbacks registered by the React main thread.

### Phase 5: Universal React Adapter (`frontend/src/api.ts`)

Create an `ApiAdapter` interface with two methods: `executeCli(args)` and `subscribe(topic, callback)`.

* If `window.go` exists (Wails), route calls to Wails IPC and `runtime.EventsOn`.
* If not (Web), spawn `worker.ts` and route calls via Comlink.

### Phase 6: React UI Integration

Build a custom hook (e.g., `useEngineEvent`) that subscribes to the engine's events via the `ApiAdapter`. When an event like `"data-changed"` fires, trigger a state invalidation so React re-fetches the latest state from the Go engine (via `executeCli("list-records")`).
